# Decisions

- Supplier invoices require a received GRN; PO-only invoicing (allowed in the current Angular form) is not supported by the backend — this is a deliberate scope decision, not a gap.
- Update/edit endpoints for master data and workflow documents are out of scope for this phase across all entities — create/list/approve/pay only. Edit UI shows a clear unsupported error until a later phase builds updates.
- Sales invoices require a delivered Delivery; SO-only and customer-only invoicing (allowed in the current Angular form) is not supported by the backend — same shape as the GRN requirement for supplier invoices.
- Cash in hand is cash-basis movement with no opening bank balance: O2C Collections + legacy booking Receipts (`invoice_receipts`) − Expenses (`finance_transactions` debit) − P2P Payments. Money in increases cash; money out decreases it. P2P payments and O2C collections do not post to `finance_transactions`, so they are counted here rather than being double-counted as expenses.
- Cash in Hand currently reflects only cash MOVEMENT recorded in this system (collections + receipts − expenses − payments) since data entry began — it does NOT include any opening bank balance. A business with pre-existing cash will see an artificially low or negative figure until an opening-balance mechanism is built. This is a known limitation, not a bug.
- Purchase orders may be created without a purchase request (vendor required). Converting a purchase request still requires status `approved` — same shape as sales orders / subscribed plans.
- Create-form dropdowns (GRN→Supplier Invoice, PO→Goods Receipt, SO→Delivery) fetch up to pageSize:100 to filter eligible source records — this is a raised ceiling, not true full-list filtering. If any of these entities exceed 100 open/eligible records for a single org, the dropdown will silently miss some valid options. Acceptable for now given current data volume; revisit with server-side filtering (e.g. a status query param) if that becomes a real constraint.
- List query filters the APIs actually honor (beyond `page` / `page_size`): O2C quotations and sales orders (`customer_id`, `status`, `search`); P2P vendors (`status`, `search` on name/email/GST), purchase requests and purchase orders (`vendor_id`, `status`, `search`), goods receipts (`status`, `search` on GRN/PO/vendor), supplier invoices (`vendor_id`, `status`, `search` on invoice/vendor/PO), payments (`search` on invoice/vendor/mode), payables (`vendor_id`, `status`, `search` on invoice/vendor); products (`search`, `status`); bookings and legacy invoices (`customer_id`). Date filtering is not implemented — none of these list APIs have a date query param. Create-form eligibility stays client-side on that 100-row fetch.
- Expense create form collects GST amount, category, SKU, and attachments, but finance_transactions only persists amount/date/description/optional vendor reference — the other fields are silently accepted and dropped. This is a known gap, not a bug. Either extend finance_transactions to store them, or remove those fields from the Angular form so users aren't misled into thinking they're saved — decide which before this goes further; don't leave it silently dropping data indefinitely.
- Decision on that gap: do not extend the schema yet. The Angular Expense form (and list columns) show only what finance_transactions actually stores: date, cost, description, optional vendor. GST/category/SKU/quantity/unit price/status/attachments stay out of the form until a later schema decision. Extending finance_transactions (or reviving the leftover `expenses` table with P2P vendor/category FKs) is the wrong default — it would invent a mini GL / couple expenses to unbuilt master data.
- The dashboard "Expense by category" chart was removed for the same reason: finance_transactions has no category column, so the chart had nothing real to show. Do not restore it (and do not wire `/dashboard/categories`) until category is stored as a first-class field. Seed data on that endpoint is not a substitute.
- First expense per org auto-creates an internal 'Operating cash' finance_accounts row (account_id is NOT NULL on finance_transactions). This is an implicit single-account model, not a real Accounts module — do not build multi-account support, transfers, or account selection UI without a deliberate decision to do so.
- audit_logs is append-only via a database trigger (audit_logs_append_only), not via REVOKE, because Postgres table owners retain privileges regardless of REVOKE grants. The app's bfms role is the table owner, so true privilege-level enforcement would require a separate non-owner migration role — not implemented. The trigger is the actual enforcement mechanism; it can be bypassed only via the app.allow_audit_delete session GUC, which must never be set outside test fixtures.
- O2C "Subscribed Plan" is the user-facing name for rows in `o2c_quotations`. The table, routes, and JSON fields (`quoteNumber`, `quotationId`) stay as-is. `plan_duration` is INTEGER days (nullable; create form defaults to 30). `billing_cycle` is stored but does not yet drive recurring invoice generation — that is a future phase. One invoice per plan is the current billing model.
- Subscribed-plan `deposit_amount` is plan metadata only — it does not auto-flow into the Sales Invoice amount. Same shape as legacy Booking "Security paid", which is stored and shown separately (`security_paid` / `securityAmountDeposited`) rather than added into invoice `amount`. Refund/adjustment at plan end is a later phase.
- GSTIN remains on `customer_skg` (nullable) and on vendor/GST paths. The rental customer create form hides it — it is optional for rental subscribers, not deleted.
- Customer photo and address-proof files are stored on the existing `documents` table (`storage_key` + `file_data` BYTEA). `POST /api/v1/documents` stores the file; `GET /api/v1/documents` lists them; `GET /api/v1/documents/{id}/content` re-checks tenant ownership before serving bytes. No public URL is ever issued. This is not a full documents module (no versioning, folders, or sharing). Leftover BYTEA columns on `customer_skg` from an earlier KYC attempt are no longer written.
- Document files are currently stored as BYTEA directly in the documents table (`file_data` column), not external object storage. This is a deliberate MVP choice — acceptable at current scale, but will not scale well if document volume/size grows significantly. Revisit with real object storage (S3-compatible) if that becomes a constraint.
- `POST /api/v1/documents` accepts PNG, JPEG, and PDF only, with a 10 MB size cap. Customer photo is PNG/JPEG; address proof may also be PDF. Anything else is 422.
- Vendor, customer, and subscribed-plan (quotation) creates do not write `audit_logs` today. Payments, collections, approvals, expenses, and admin user changes do. Close that gap when convenient — master-data creates should be audited the same way as other mutations once this is real money. Not blocking.
- Dashboard "Recent expenses", "Recent invoices", and "Recent receipts" are live tenant-scoped last-N queries (`finance_transactions` expense debits; O2C sales invoices union legacy `invoice_skg`; O2C collections union `invoice_receipts`). Expense `category` is always `"—"` because there is no category column — do not invent one. The Expense vs Income chart (`GET /dashboard/income`) is the same cash-basis formula as the KPI cards, bucketed by day (last 7), week (last 4), or month (last 6). Product summary (`/dashboard/products`, `/product/{id}`) stays seed scaffolding; the Angular dashboard hides that section with the coming-soon pattern and does not call it. `/dashboard/categories` remains unused. Remaining seed functions in `dev_seed.py` are not deleted.
- CORS is an exact allow-list from `CORS_ORIGINS`. Production is pinned to the real frontend origin. There is no `allow_origin_regex` for `*.vercel.app` — a preview or unrelated Vercel app must not be able to call this API.
- A draft purchase order is issued with `PATCH /p2p/purchase-orders/{id}/issue` (`create` permission — same as PO create, so OPERATOR can issue). A draft subscribed plan is accepted or rejected with `PATCH /o2c/quotations/{id}/accept` and `.../reject` (`approve` permission — same as invoice approval, so OPERATOR cannot). Both reject any status other than `draft` with 400. This closes the previous dead-end where a draft record could not move forward.
- **Assumption (GST):** Single flat `gst_amount` per invoice. No CGST/SGST/IGST split. GST is stored, not auto-applied to totals. GST Summary aggregates stored `gst_amount` on non-cancelled P2P supplier invoices (input) and O2C sales invoices plus legacy `invoice_skg` rows with `is_gst_invoice = true` (output). Expense GST is not stored on `finance_transactions`, so it is reported as 0. There is no tax calculation engine.
- **Assumption (Accounts):** The implicit single "Operating cash" `finance_accounts` row is the only account. The Accounts page is read-only; balance is CashPositionService net (collections + receipts − expenses − payments), not the unused `finance_accounts.balance` column. No multi-account support, transfers, or create UI.
- **Assumption (Reconciliation):** No bank feed exists. The page is a static "not connected" state plus one org-scoped free-text note (`reconciliation_notes`). Saving a note does not match, post, or unpost anything.
- **Assumption (Income):** Cash-basis derived list: completed `o2c_collections` + `invoice_receipts` only. Accrual invoice rows are not shown. There is no manual income posting form.
- **Assumption (P&L report):** Cash-basis, same formula as dashboard net cash movement — not an accrual P&L. Named "P&L (cash-basis)" / `financial-summary` so it is not mistaken for a statutory P&L.
- **Assumption (Transactions):** List is `finance_transactions` only (today: expense debits). P2P payments and O2C collections stay on their own pages and are not merged here.
- **Assumption (Legacy bookings):** `booking_skg` / `invoice_skg` / `invoice_receipts` already existed and now have real APIs. Parallel to O2C, not a replacement. `plan_skg` has no API; booking invoices no longer send seed plan IDs (plan_id stays nullable). Receipt outstanding is computed from stored receipts, not from a seed store.
- **Assumption (Documents workspace upload):** Workspace uploads use `entityName=organization` and `entityId=<org UUID>`. PNG/JPEG/PDF, 10 MB, same as customer KYC. List is `GET /documents`.
- **Assumption (Reports index):** Live reports are Purchase, Sales, Payables, Receivables, Cash Flow, GST Summary, and P&L (cash-basis) only. Angular registers those seven routes; former index cards (expense/income/audit/vendor/customer/product/invoice/receipt) are not in the live set.
- **Assumption (Master data RBAC):** Deliberate split, matching each Angular page's `canEdit` — not a copied-from-PR oversight. Vendor list, customer list, vendor detail, customer detail, and Reference Data use `canMaintainReference` (ADMIN/MANAGER only); vendor/customer/reference POST endpoints use `maintain_reference`. OPERATOR/FINANCE do not see Add/Edit vendor or customer, and they do not see the vendor-detail "New purchase request" / customer-detail "New subscribed plan" shortcuts — they still create PRs and plans from those modules' own list pages (`create`). Product, category, and service list pages use `hasPermission(role, 'create')`, so OPERATOR and FINANCE see Add and can POST catalog rows (SKU/offering maintenance). Backend product/category/subcategory/offering create stays on `create` to match that UI. Updates remain 501.
